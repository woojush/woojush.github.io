## 2. 후보별 분석

### 2.1 Astro

| 기준 | 평가 |
|------|------|
| 유지보수성 | 상 — 콘텐츠(Markdown)와 코드가 분리되고, 핵심 개념(파일 기반 라우팅, 컴포넌트, 컬렉션)이 단순. 단점: 메이저 버전 변화가 잦은 편이라 버전 고정이 필요 |
| Markdown 관리 | **상** — Content Collections가 Zod 스키마로 frontmatter를 빌드 시 검증. 오타·누락이 빌드 에러가 됨 |
| 커스터마이징 | 상 — 기본 스타일이 거의 없는 빈 캔버스. `.astro` 컴포넌트는 HTML에 가까워서 디자인 의도를 그대로 옮기기 쉬움 |
| 성능 | 상 — 기본이 **JS 0**. 글 페이지는 순수 HTML+CSS, 인터랙션이 필요한 부분만 JS를 로드 |
| GitHub Pages | 상 — 공식 GitHub Actions 배포 가이드가 있음 |
| Claude Code 작업성 | 상 — 구조가 규칙적이고 타입/스키마 에러가 구체적 |
| 인터랙티브 확장 | 상 — MDX에서 컴포넌트를 import하고, 필요한 컴포넌트만 "island"로 hydrate |

### 2.2 Next.js (static export)

| 기준 | 평가 |
|------|------|
| 유지보수성 | 중 — 생태계는 가장 큼. 반면 정적 export는 프레임워크의 주 사용 방식이 아니어서 일부 기능에 제약이 있고, 앱 라우터·번들러 등 큰 변화를 따라가야 함 |
| Markdown 관리 | 중하 — MDX 파이프라인과 콘텐츠 스키마 검증을 직접 조립해야 함. 이 용도의 서드파티 도구(Contentlayer 등)는 유지보수가 불안정했던 전례가 있어, 의존할 만한 표준이 약함 |
| 커스터마이징 | 상 |
| 성능 | 중 — 정적 글 페이지에도 React 런타임이 번들에 포함됨 |
| GitHub Pages | 중 — 가능하지만 `basePath`, 이미지 최적화 비활성 등 설정이 필요 |
| Claude Code 작업성 | 상 — 학습 데이터가 가장 풍부 |
| 인터랙티브 확장 | **상** — 전부 React라서 시각화를 가장 자연스럽게 넣을 수 있음 |

> 언제 Next가 맞나: 사이트 자체가 로그인, DB, 서버 로직이 있는 **앱**이 될 때. 이 브리프는 "글이 쌓이는 정적 아카이브"이므로 Next의 강점이 쓰이지 않는다.

### 2.3 Jekyll

| 기준 | 평가 |
|------|------|
| 유지보수성 | 중하 — Ruby 툴체인(gem, bundler) 관리가 필요하고, 생태계가 정체 중 |
| Markdown 관리 | 중하 — 스키마 검증 없음. 오타가 조용히 빈 값이 됨 |
| 커스터마이징 | 중 — Liquid 템플릿에는 컴포넌트 개념이 약함 |
| 성능 | 상 |
| GitHub Pages | 상 (가장 오래된 네이티브 경로) — 단, 내장 빌드는 허용 플러그인이 제한적이라 결국 Actions를 쓰게 됨 |
| Claude Code 작업성 | 중 |
| 인터랙티브 확장 | 하 — 컴포넌트 모델이 없어서 `<iframe>`이나 raw HTML 삽입에 의존 |

### 2.4 Hugo

| 기준 | 평가 |
|------|------|
| 유지보수성 | 상 — 단일 바이너리, 빌드가 매우 빠르고 의존성이 적음 |
| Markdown 관리 | 중 — 분류(taxonomy)는 강력하지만 frontmatter **타입 검증은 없음** |
| 커스터마이징 | 중 — Go 템플릿 문법이 독특해서 디자인 작업 시 진입장벽이 있음 |
| 성능 | 최상 |
| GitHub Pages | 상 |
| Claude Code 작업성 | 중 — 템플릿 오류 메시지가 불친절한 편 |
| 인터랙티브 확장 | 중하 — shortcode로 가능하나 컴포넌트 단위 재사용·상태 관리는 불편 |

> Hugo가 이기는 상황: 글이 수천 개라서 **빌드 속도**가 병목이 될 때. 개인 아카이브가 그 규모가 되려면 오랜 시간이 걸리므로 지금 기준으로는 이점이 크지 않다.

## 4. 추천: Astro

### 4.1 이유 — 요구사항별로 어떤 기능이 어떤 문제를 푸는가

| 이 사이트의 요구 | Astro의 기능 | 그래서 가능해지는 것 |
|------------------|-------------|---------------------|
| frontmatter의 `status`, `topic`, `links`가 일관돼야 함 (02 문서) | **Content Collections + Zod 스키마** | `status: grwoing` 오타나 존재하지 않는 slug를 가리키는 `links`가 **빌드 에러**로 잡힘. 배포 후에 발견하는 일이 없음 |
| 파일 위치와 URL이 일치하고, 주제를 바꿔도 URL이 유지돼야 함 | **파일 기반 라우팅 + `[slug].astro`** | `content/knowledge/projection.md` → `/knowledge/projection`. topic은 frontmatter 속성이라 URL과 무관 |
| 글 페이지에 JS가 거의 없어야 함 | **기본 JS 0 (islands)** | 수식·코드가 많은 글도 HTML+CSS만으로 렌더링. 테마 토글 같은 필요한 곳에만 소량의 스크립트 |
| 수학 시각화를 글에 embed | **MDX + 컴포넌트 import, `client:visible`** | 글에서 `<Embed>`로 넣고, 화면에 보일 때만 로드 |
| Home의 최근 글, 태그 페이지, 지식 트리를 자동으로 만들기 | **`getCollection()` + 정적 페이지 생성** | 파일만 추가하면 목록·트리·태그 페이지가 빌드 시 갱신 |
| Claude Code가 안전하게 수정 | **규칙적 폴더 구조 + 구체적 빌드 에러** | "무엇을 어디에 추가하는가"가 명확하고, 실수하면 빌드가 고칠 위치를 알려줌 |
| GitHub Pages | **공식 Actions 워크플로** | push하면 자동 빌드·배포 |

### 4.2 Astro를 고르면 생기는 약점과 대응

| 약점 | 대응 |
|------|------|
| 메이저 버전 변화가 잦다 (v0.1 작성 시 Astro 6로 알고 있었으나, 구현 시점인 2026-10-04의 npm 최신 안정 버전은 **Astro 7.3.5**, Node ≥ 22.12 필요) | `package.json`에서 버전을 고정하고, 업그레이드는 별도 작업으로 분리. 콘텐츠가 Markdown이라 프레임워크가 바뀌어도 콘텐츠는 이식 가능 |
| React 중심의 대형 UI 앱에는 불리 | 필요 시 React/Svelte 등을 "island" 통합으로 나중에 추가. 구조 변경 없이 추가 가능 |
| Next보다 생태계가 작다 | 이 사이트에 필요한 기능(MDX, 사이트맵, KaTeX 연동)은 공식 통합과 remark/rehype 플러그인으로 충족됨 |

**콘텐츠 이식성**: 모든 글이 표준 Markdown + YAML frontmatter이므로, 10년 뒤 Astro가 맞지 않아도 `content/` 폴더는 다른 도구로 옮길 수 있다. 이 사이트에서 진짜 자산은 코드가 아니라 `content/`이므로, 이 점이 프레임워크 선택의 위험을 낮춘다.

## 5. 기능별 구현 방식 (설계 수준)

| 기능 | 방식 | 비고 |
|------|------|------|
| Markdown / MDX | Astro 내장 + `@astrojs/mdx` | `.md` 기본, 컴포넌트 필요 시 `.mdx` |
| 수식 (LaTeX) | `remark-math` + `rehype-katex` (빌드 시 HTML 변환) | 브라우저에서 수식 JS를 돌리지 않음. KaTeX CSS는 글 레이아웃에서 로드 |
| 코드 하이라이팅 | Astro 내장 Shiki, 라이트/다크 듀얼 테마 | 빌드 시 처리 |
| 다이어그램 | Mermaid, **클라이언트 지연 로드** | ```` ```mermaid ```` 블록이 있는 페이지에서만 Mermaid를 로드. Shiki에서는 mermaid 언어를 제외. 대안으로 빌드 시 SVG 렌더링도 있으나 헤드리스 브라우저 의존이 생겨 유지보수 부담이 큼 |
| 인터랙티브 (1단계) | **`public/labs/<slug>/index.html` + `<Embed>` (iframe)** | 어떤 HTML 파일이든 넣을 수 있음. 글과 완전히 분리되어 서로를 깨뜨리지 않음 |
| 인터랙티브 (2단계) | MDX에서 컴포넌트 import + `client:visible` | 테마·상태를 글과 공유해야 할 때. 필요해지는 시점에 프레임워크 통합 추가 |
| 다크/라이트 | CSS 변수 + `data-theme` 속성, 첫 페인트 전 인라인 스크립트로 적용 | 화면 깜빡임(flash) 방지. 상세는 04 문서 |
| 사이트 목차(TOC) | Astro가 제공하는 heading 목록으로 생성 | 글 페이지 전용 |
| 검색 | **MVP 제외.** 필요 시 Pagefind (정적 사이트용, 빌드 후 인덱스 생성) | 글이 많아졌을 때 추가해도 구조 변경 없음 |
| 사이트맵 / RSS | `@astrojs/sitemap` 등 공식 통합 | Phase 5에서 선택적으로 |
| 이미지 | Astro 내장 이미지 처리 | 이미지 확대(zoom)는 후순위 |

### 인터랙티브 두 단계를 나눈 이유 (구체적 사례)

"Projection Visualizer"를 만들었다고 하자.

- **1단계 (iframe)**: 단독 HTML 파일(`public/labs/projection/index.html`)로 완성하고, 글에서는 `<Embed src="/labs/projection/" title="Projection visualizer" height={420} />` 한 줄만 쓴다. 장점: 이 파일은 사이트 코드와 무관하게 작동하므로, 사이트 디자인을 개편하거나 프레임워크를 교체해도 깨지지 않는다. 단점: 사이트의 다크 모드와 자동 연동되지 않는다.
- **2단계 (컴포넌트)**: 시각화가 사이트 테마와 상호작용해야 할 때(예: 다크 모드에서 색을 바꿈) 컴포넌트로 승격한다. 승격은 선택 사항이며, 1단계로 만든 것을 그대로 두어도 된다.

MVP는 **1단계만** 구현한다. 2단계는 실제로 필요해지는 시점에 추가한다.

## 6. 배포

- **호스팅**: GitHub Pages. 빌드는 GitHub Actions에서 수행하고, `main`에 push하면 자동 배포.
- **저장소 이름에 따른 URL**:
  - `<username>.github.io` 저장소 → `https://<username>.github.io/` (루트 경로, 설정 단순)
  - 그 외 이름 → `https://<username>.github.io/<repo>/` (`base` 설정 필요, 모든 링크가 이 경로를 따라야 함)
  - 커스텀 도메인을 쓰면 루트 경로가 되어 `base`가 불필요
- **저장소 공개 여부**: 무료 플랜에서는 보통 public 저장소가 필요하다 (플랜 정책은 변경될 수 있으니 확인). public이면 `draft: true` 글도 **소스에서는 누구나 볼 수 있다.** 공개하기 싫은 초안은 저장소 밖에서 쓰거나 로컬에만 둬야 한다.
- **버전 정책**: Node 버전 고정(`.nvmrc`), Astro와 주요 플러그인 버전 고정, 업그레이드는 독립된 커밋.
- **패키지 매니저**: npm (가장 단순). 별도 이유가 없는 한 pnpm/yarn으로 넓히지 않는다.
- **Actions 버전 (2026-10-04 확인)**: `actions/checkout@v7`, `withastro/action@v6`, `actions/deploy-pages@v5`. 메이저 태그를 사용하며, 정기적으로 확인한다.

## 7. 선택 취소 조건 (이 결정을 다시 볼 신호)

아래가 *실제로* 발생하면 스택을 재검토한다.

1. 사이트에 로그인/DB/서버 기능이 필요해졌다 → 서버가 있는 프레임워크 검토
2. 글이 수천 개가 되어 Astro 빌드 시간이 불편해졌다 → Hugo 검토
3. 시각화가 대부분 React 앱이고 글보다 앱이 중심이 되었다 → Next 검토

이 경우에도 `content/` 폴더(Markdown + YAML)는 그대로 가져갈 수 있다.
