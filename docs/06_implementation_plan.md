## 1. MVP 범위

### 1.1 MVP에 포함 (구현한다)

| 영역 | 포함 기능 | 포함하는 이유 |
|------|----------|---------------|
| 정보 구조 | 5개 메뉴, 세 컬렉션(knowledge/projects/writing), `/tags/[tag]` | 구조가 곧 이 프로젝트의 본체 |
| 콘텐츠 모델 | frontmatter 스키마 검증, `links` + 자동 backlink, `topic` 트리 자동 생성 | 이후 모든 글이 이 모델 위에 쌓이므로 처음에 맞아야 함 |
| HOME | 정체성 소개 + NOW + Recent knowledge/writing + Selected projects (비어 있으면 숨김) | |
| ABOUT | 본문 + Timeline | |
| 글 읽기 | Markdown, KaTeX, Shiki, TOC, Mermaid(지연 로드), `<Embed>`(iframe) | 브리프 14번이 "반드시"로 요구한 확장 포인트가 실제로 동작함을 증명 |
| 디자인 | 토큰 시스템, 다크/라이트(3상태, flash 없음), 반응형 헤더, 포커스·키보드 기본 | |

### 1.2 MVP에서 제외 (나중으로 미룬다)

| 기능 | 미루는 이유 | 도입 신호 |
|------|-------------|-----------|
| 전문 검색 (Pagefind 등) | 글이 적을 때는 목록과 태그로 충분 | 글 30~50편 이상, 찾느라 시간이 걸리기 시작 |
| 이미지 확대(zoom) | 글에 이미지가 많아지기 전에는 불필요 | 도표가 많은 글이 생길 때 |
| 키보드 단축키 (`/`, `j/k`) | 기본 Tab 이동과 skip link로 충분 | 글 이동이 잦아져 불편할 때 |
| Writing의 kind 필터 페이지 | 글이 적음 | 글 20~30편 이상 |
| RSS / OG 이미지 자동 생성 | 공유 필요가 아직 없음 | 글을 외부에 공유하기 시작할 때 (RSS는 Phase 5 선택) |
| 인터랙티브 2단계 (컴포넌트 island) | iframe으로 충분히 시작 가능 | 시각화가 사이트 테마/상태와 상호작용해야 할 때 |
| `[[위키링크]]` 문법, 그래프 뷰 | `links` 필드로 필요한 관계는 표현됨 | 문서가 많아져 본문 중 링크 입력이 번거로울 때 |
| 다국어 라우팅 (`/ko`, `/en`) | 글 단위 `lang` 필드로 시작 | 같은 글을 두 언어로 제공하고 싶을 때 |
| `/now` 단독 페이지, NOW 아카이브 | Home의 NOW로 충분. 과거 NOW는 git에 남음 | 변화 이력을 공개하고 싶을 때 |
| 댓글, 방문자 통계, 뉴스레터 | 개인 아카이브의 목적과 무관 | 필요가 생기면 개별 검토 |
| CMS(웹 편집기) | Markdown + Claude Code가 편집 도구 | 파일 편집이 병목이 될 때 |
| 이력서 PDF 생성, `/uses` 등 부가 페이지 | 메뉴 확장 규칙(01 문서 7절) | 규칙 충족 시 |

## 2. 구현 단계

각 단계를 **무엇을 할 수 있게 되는가 / 왜 이 순서인가 / 완료 기준**으로 적었다. 단계마다 독립된 커밋(또는 브랜치)으로 남기고, 다음 단계 시작 전에 사용자가 결과를 확인한다.

### Phase 0. 뼈대와 안전장치

| | |
|---|---|
| **만드는 것** | Astro 프로젝트 초기화, TypeScript strict, 버전 고정(`.nvmrc`, 패키지 버전), `content.config.ts`에 세 컬렉션과 스키마, `CLAUDE.md`, `docs/`에 이 설계 문서 복사, GitHub Actions 배포 워크플로, 빈 페이지 하나 |
| **무엇이 가능해지나** | "푸시하면 실제 URL에 반영된다"는 파이프라인과 "frontmatter를 잘못 쓰면 빌드가 막는다"는 검증이 **글 하나 쓰기도 전에** 작동한다 |
| **왜 첫 번째인가** | 배포가 안 되는 상태로 쌓은 작업은 마지막에 한꺼번에 문제가 터진다. 가장 위험한 부분(Pages의 `site`/`base` 설정, 스키마)을 가장 작은 상태에서 먼저 검증한다 |
| **완료 기준** | ① 빈 사이트가 실제 GitHub Pages URL에서 열림 ② 일부러 틀린 frontmatter(`status: grwoing`)를 넣으면 `npm run build`가 실패하고 에러가 파일·필드를 가리킴 ③ `CLAUDE.md` 작성 완료 |

### Phase 1. 디자인 토큰과 사이트 틀

| | |
|---|---|
| **만드는 것** | `tokens.css`, `base.css`, 서체 self-host, `BaseLayout`, `Header`/`Nav`/`Footer`, `ThemeToggle` + 첫 페인트 전 테마 초기화, skip link, 포커스 스타일 |
| **무엇이 가능해지나** | 모든 페이지가 같은 틀과 룩을 공유한다. 포인트 색이나 본문 크기를 **토큰 한 줄로** 바꿀 수 있다 |
| **왜 이 순서인가** | 페이지를 만들기 전에 틀이 있어야 이후 모든 페이지가 자동으로 같은 룩을 얻는다. 나중에 틀을 만들면 페이지마다 스타일을 다시 손봐야 함 |
| **완료 기준** | ① 라이트/다크/시스템 전환이 되고 새로고침 시 번쩍임 없음 ② 모바일 폭에서 헤더가 깨지지 않음 ③ 키보드만으로 메뉴 이동 가능, 포커스가 보임 ④ 대비 4.5:1 이상 확인 |

### Phase 2. 글 읽기 파이프라인 (+ 검증용 샘플 1편)

| | |
|---|---|
| **만드는 것** | `prose.css`, `ArticleLayout`, `TableOfContents`, KaTeX·Shiki 설정, Mermaid 지연 로더, `Embed`/`Callout`/`Figure`, 상세 페이지 라우트 3종 |
| **무엇이 가능해지나** | Markdown에 수식·코드·다이어그램·인터랙티브 시각화를 넣은 글이 읽기 좋게 나온다 |
| **왜 이 순서인가** | 이 사이트의 핵심 가치는 "읽히는 글"이다. 목록 페이지나 Home보다 **글 한 편이 제대로 나오는지**를 먼저 확인해야 이후의 모든 설계가 의미가 있다 |
| **검증용 샘플** | `knowledge/projection.md` 한 편(수식, 코드, Mermaid, `<Embed>`를 모두 포함). 내용은 임시이며 사용자가 직접 쓴 글로 교체하는 것을 전제로 한다. 샘플은 사용자 글이 생기면 삭제하거나 `draft: true`로 전환 |
| **완료 기준** | ① 수식 인라인/블록, 코드(라이트/다크), Mermaid, Embed가 한 글에서 모두 보임 ② 다크 전환 시 모두 따라서 바뀜 ③ 글 페이지의 JS 전송량이 작음 (Mermaid가 없는 글에서는 Mermaid를 로드하지 않음) ④ 모바일에서 긴 수식·코드가 페이지를 옆으로 밀지 않음 |

### Phase 3. 목록과 관계

| | |
|---|---|
| **만드는 것** | `lib/content.ts`, `lib/topics.ts`, `lib/links.ts`, `EntryRow`/`EntryList`/`TopicTree`/`Related`/`TagList`, 세 목록 페이지, `/tags/[tag]`, 프로젝트 상세의 `ProjectHeader` |
| **무엇이 가능해지나** | 파일을 추가하면 목록·트리·태그 페이지가 갱신되고, 한쪽에서 선언한 `links`가 양쪽 페이지에 나타난다 |
| **왜 이 순서인가** | 목록은 "글이 있어야" 의미가 있으므로 상세 페이지 뒤에 만든다. 관계 계산(backlink)은 규칙이 가장 복잡한 부분이라 데이터 흐름이 정리된 뒤에 넣는다 |
| **완료 기준** | ① 샘플 knowledge 1편 + project 1편 + writing 1편을 서로 `links`로 연결했을 때 세 페이지에 Related가 올바르게 표시 ② 존재하지 않는 slug를 `links`에 쓰면 빌드 실패 ③ `draft: true`는 프로덕션 빌드에 나타나지 않음 ④ 콘텐츠가 없는 섹션/topic은 화면에서 숨겨짐 |

### Phase 4. HOME과 ABOUT

| | |
|---|---|
| **만드는 것** | `NowBlock`, `Timeline`, Home 페이지, About 페이지, `data/now.yaml`, `data/timeline.yaml`, `data/site.ts` |
| **무엇이 가능해지나** | 사이트의 입구가 완성된다. `now.yaml`만 고치면 Home이 현재의 나를 보여준다 |
| **왜 이 순서인가** | Home은 다른 영역을 **요약해서 보여주는** 페이지라서 요약할 대상(목록, 관계)이 완성된 뒤에 만든다. 또한 Home과 About의 소개 문구는 사용자의 직접적인 입력이 필요한데, 앞 단계가 진행되는 동안 문구를 준비할 시간이 생긴다 |
| **완료 기준** | ① `now.yaml`에 행을 하나 추가하면 코드 수정 없이 Home에 반영 ② 콘텐츠가 비어 있는 섹션은 숨겨지고 NOW와 소개만으로도 어색하지 않음 ③ Timeline이 모바일에서도 읽힘 |

### Phase 5. 마감

| | |
|---|---|
| **만드는 것** | 404, 메타태그(제목/설명/OG 기본), 사이트맵, favicon, 접근성 점검, 성능 점검, README 보강, (선택) RSS |
| **무엇이 가능해지나** | 공개해도 부끄럽지 않은 상태. 링크를 공유했을 때 제목/설명이 정상 표시 |
| **왜 마지막인가** | 마감은 모든 페이지가 존재해야 한 번에 점검할 수 있다 |
| **완료 기준** | ① Lighthouse(접근성, 성능, SEO) 모두 90점대 이상을 목표로 점검 ② 모든 페이지 제목 위계 정상 ③ README만 보고 새 글을 추가하고 배포할 수 있음 |

## 3. 작업 방식

- 한 번에 한 Phase만 진행하고, 끝나면 **완료 기준을 하나씩 확인한 결과를 보고**한다.
- 각 Phase는 되돌릴 수 있게 독립 커밋으로 남긴다.
- 계획에 없던 기능이 필요하다고 판단되면 **구현하지 않고 먼저 제안**한다. (브리프 17번: 처음부터 모든 기능을 구현하지 않음)
- 콘텐츠(실제 글)는 사용자가 쓴다. 구현 중에 생기는 샘플은 사용자 글로 교체하기 전까지의 임시 자료로 명확히 표시한다.

## 4. 위험과 대응

| 위험 | 가능성 | 영향 | 대응 |
|------|:---:|------|------|
| GitHub Pages의 `base` 경로 설정 실수로 링크/자산이 깨짐 | 중 | 배포 후 CSS가 안 먹거나 링크가 404 | Phase 0에서 빈 사이트로 먼저 검증. 저장소 이름 결정을 먼저 받는다 |
| 스키마를 너무 엄격하게 잡아서 글쓰기가 번거로워짐 | 중 | 글을 안 쓰게 됨 | 필수 필드는 최소(`title`, `date`, 그리고 type별 1~2개)로 유지. 나머지는 선택 |
| 설계가 과해져서 글보다 사이트 만지는 시간이 길어짐 | 중 | 사이트가 목적이 됨 | MVP 제외 목록을 지키고, 도입 신호가 실제로 나타나기 전에는 추가하지 않음 |
| Astro 메이저 업그레이드로 빌드가 깨짐 | 중 | 한동안 빌드 불가 | 버전 고정, 업그레이드는 별도 브랜치에서. 콘텐츠는 표준 Markdown이라 보호됨 |
| 한글 폰트 용량으로 첫 로딩이 느려짐 | 중 | 성능 | 동적 서브셋 + self-host. Phase 1에서 실측 |
| Mermaid/KaTeX가 다크 모드에서 어색함 | 낮음 | 가독성 | Phase 2의 완료 기준에 다크 전환 확인을 포함 |

### 결정이 필요한 사항

| # | 질문 | 선택지 | 추천 | 추천 이유 |
|---|------|--------|------|-----------|
| 1 | **사이트 언어** | (a) 한국어 중심 (b) 영어 중심 (c) 글마다 `lang`으로 지정, UI 문구는 영어 | **(c)** | 글의 언어를 글 단위로 고르면 이후 방향이 바뀌어도 사이트 구조를 건드리지 않음 |
| 2 | **저장소 이름 / 도메인** | (a) `<username>.github.io` (b) 다른 이름의 프로젝트 사이트 (c) 커스텀 도메인 | **(a) 또는 (c)** | 루트 경로가 되어 `base` 설정 문제가 없음 |
| 3 | **저장소 공개 여부** | public / private | **public** | 무료 플랜에서 Pages 사용에 일반적으로 필요. 단, 초안 글은 소스에서 보임 |
| 4 | **About에 공개할 정보 범위** | 이름, 사진, 학교, 군 복무 언급 여부, 연락처 | 사용자가 결정 | 공개 후 되돌리기 어려운 정보라서 설계가 아니라 본인의 판단이 필요 |
| 5 | **메뉴 표기** | (a) `about knowledge …` 소문자 (b) 브리프의 대문자 `ABOUT …` | **(a)** | 대문자 라벨은 생성형 디자인에서 흔한 기본값이고 한글 사이트와의 어울림도 약함 |
| 6 | **본문 서체** | (a) Pretendard 한 가족 (b) 본문 serif | **(a)** | 한글 serif는 용량이 크고 라틴 서체와의 짝맞춤이 필요해 초기 부담이 큼. 나중에 토큰 변경으로 교체 가능 |
| 7 | **`type` 지정 방식** | (a) 폴더가 곧 type (b) frontmatter에 `type:`도 기재 | **(a)** | 같은 정보를 두 곳에 두면 어긋날 수 있음 |
| 8 | **knowledge 성숙도 표시(`seed/growing/evergreen`)** | 쓴다 / 쓰지 않는다 | **쓴다** | 완성되지 않은 글을 부담 없이 올릴 수 있어 정원형 아카이브에 맞음 |
| 9 | **MDX 사용 범위** | (a) 기본 `.md`, 임베드가 필요한 글만 `.mdx` (b) 전부 `.mdx` | **(a)** | `.md`는 표준이라 이식성이 높고 도구 의존이 적음 |

위 항목 외에 설계에 대한 수정 요청이나 질문이 있으면 함께 알려주면 된다.
